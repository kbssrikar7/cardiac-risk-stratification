# Infarct-Burden-Augmented Cardiac Risk Stratification: Methods and Results

Internal technical report. Written as a shared basis for a paper Methods/Results section and a provisional patent's enabling disclosure - both need the same precise, honest account of what the system does and why. Not a submission-ready manuscript.

## 1. Data

EMIDEC dataset, 150 patients: 100 with ground-truth segmentation masks (training set), 50 without (test set). Each mask uses a 5-class convention: `0=background, 1=LV cavity, 2=myocardium, 3=infarction, 4=no-reflow (microvascular obstruction)`. Sourced via a Kaggle mirror (`johnsonhk88/emidec-dataset-for-heart-mri-image`, MIT licensed) after registration on the canonical `emidec.com` distribution failed.

Each patient also has 4 clinical variables (age, LVEF, troponin, NT-proBNP) and a 4-class risk label (`Risk_Score`) generated by a deterministic rule engine applied to those same 4 variables - not an observed clinical outcome. This is a material limitation: because the same 4 values are both model inputs and (via the rule) the training target, part of what every classifier learns is a reproduction of the labeling rule itself. The radiomics/imaging-derived features are the only information source not already fully determined by the label formula, which is exactly why the imaging pipeline is where this work's technical contribution lives.

## 2. Bug fix: myocardium radiomics features were extracted from the wrong region

The original pipeline extracted PyRadiomics features using `label=1` uniformly across all 150 patients. For the 50 test patients, masks are model-predicted with `label=1` explicitly meaning myocardium - correct. For the 100 training patients, masks are the raw EMIDEC ground truth, where `label=1` is the LV cavity and `label=2` is myocardium. **Two-thirds of the dataset's "myocardial" radiomics features were describing the blood pool, not the heart muscle.**

Fix: `label=2` for ground-truth masks. Validated by comparing corrected per-patient myocardial tissue volumes against the dataset's own published summary statistics - all comparisons matched (see Section 4 for the analogous validation of the new infarct-burden features, same method). Radiomics were re-extracted for all 150 patients (0 failures) into `combined_radiomics_features_FIXED.csv`.

## 3. Evaluation protocol

All final metrics use repeated stratified 5-fold cross-validation (5 repeats, 25 folds total), not a single train/test split - at n=150 with a class distribution as skewed as this one (majority class ~75%), a 20% holdout leaves too few minority-class samples per fold for a stable estimate. Hyperparameters are selected via a nested Optuna search (60 trials, 5-fold CV objective, macro-AUC) inside each outer evaluation, so the reported metrics are not contaminated by the search itself. Class imbalance is handled via a fixed `RandomUnderSampler` + `SMOTE` pipeline applied only to each fold's training split.

The originally-deployed model was a stacked ensemble of XGBoost and an Attention-MLP, combined via a meta-learner. Two problems were found and fixed here: (1) the meta-learner's training features were generated by scoring both base models on data they had already been trained on (stacking leakage, not out-of-fold), and (2) permutation importance - measured twice, before and after the label fix in Section 2, with identical results both times - showed the Attention-MLP branch contributed exactly zero signal to the ensemble (`0.0000 ± 0.0000` importance on all 4 of its output features). The ensemble was retired in favor of a single calibrated XGBoost classifier (`CalibratedClassifierCV`, sigmoid method), which matches the ensemble's accuracy with substantially less complexity. Calibration quality was verified via per-class Brier scores and a calibration curve, not merely assumed from wrapping the classifier.

Correlation-based feature pruning (dropping one member of any pair with |Pearson r| > 0.95, keeping the one with lower mean correlation to the rest of the feature set) reduced the radiomics feature count from 107 to 59, for a total of 63 features (59 radiomics + 4 clinical) with statistically identical cross-validated performance to the full 111-feature set. This became the pre-infarct-extension baseline:

| Metric | Value (mean ± std, 25 folds) |
|---|---|
| Accuracy | 0.927 ± 0.038 |
| F1 (macro) | 0.692 ± 0.116 |
| Balanced accuracy | 0.730 ± 0.123 |
| AUC (macro, OVR) | 0.974 ± 0.022 |

## 4. Novel contribution: infarct-burden feature engineering from extended segmentation

The original U-Net was trained to segment only 3 classes (background, LV cavity, myocardium); ground-truth labels 3 (infarction) and 4 (no-reflow) were collapsed into background before training, discarding them entirely. Infarct size and microvascular obstruction extent are established cardiovascular risk markers in the clinical literature - extending segmentation to preserve them, and engineering quantitative features from the result, is this work's core novel contribution. It uses only data already present in EMIDEC; no new data collection was needed.

### 4.1 Segmentation model

A U-Net with the same encoder-decoder architecture as the original 3-class model, extended to a 5-class softmax output. Training used:
- **Patient-level train/validation split** (not slice-level), preventing near-duplicate slices from the same heart volume appearing in both splits.
- **Synchronized paired augmentation**: image and mask are stacked into a single tensor before applying random flips, rotations, and translations, so both receive identical geometric transforms (an earlier attempt applying augmentation to the image only, with the mask left unmodified, collapsed myocardium Dice to ~0.0001).
- **Reflect padding** (`fill_mode="reflect"`) rather than constant/zero padding for geometric transforms, since zero-padding a one-hot mask tensor produces an invalid (non-one-hot) target at borders (an earlier attempt with constant padding caused the training loss to diverge into the trillions within a few epochs).
- **Gradient clipping** (`Adam(clipnorm=1.0)`) and post-augmentation pixel clipping as additional numerical-stability guards.
- Early stopping with `restore_best_weights=True`, capped at 150 epochs (stopped at 80).

Per-class Dice/IoU on the held-out validation patients:

| Class | Dice | IoU | Share of training pixels |
|---|---|---|---|
| Background | 0.997 | 0.995 | 96.98% |
| LV cavity | 0.884 | 0.793 | 1.48% |
| Myocardium | 0.752 | 0.602 | 1.35% |
| Infarction | 0.275 | 0.160 | 0.18% |
| No-reflow | 0.000 | 0.000 | 0.017% |

Infarction is learned non-trivially given it constitutes less than 0.2% of training pixels. No-reflow is not learned at all - at 10x rarer than infarction, it appears to be below the threshold of what a plain U-Net can extract from 100 training volumes with no further intervention (class-weighted or focal loss was not attempted; noted as future work in Section 6). This is reported as an honest negative result rather than omitted.

Collapsing the 5-class predictions back to 3 classes for a fair comparison against the original baseline shows a modest regression on the classes both models share (myocardium 0.752 vs. 0.810, LV cavity 0.884 vs. 0.926) - the 5-class model trades a small amount of 3-class accuracy for the ability to detect infarction at all. Given the infarct-burden features derived from it produce a net improvement in downstream risk classification (Section 5), this trade was judged worthwhile; the original 3-class model remains in production for the Grad-CAM myocardium-attention feature specifically, unaffected by this work.

### 4.2 Feature computation and validation

Four infarct-burden features were computed per patient: infarct volume (cm³), infarct volume as a percentage of total myocardial tissue (myocardium + infarction + no-reflow voxels - the standard clinical "infarct size" measure), no-reflow volume (cm³), and no-reflow as a percentage of infarction (the standard "microvascular obstruction extent" marker).

For the 100 training patients, features were computed directly from ground-truth masks (no model inference needed). These were validated against the EMIDEC/Kaggle dataset's own published summary statistics and matched closely: median infarct volume 20.26 cm³ (computed) vs. 20.26 cm³ (published), median no-reflow volume 2.35 cm³ vs. 2.35 cm³, 67/100 patients with any infarct vs. 67% published, 40/100 with any no-reflow vs. 40% published.

For the 50 test patients (no ground truth available), features were computed from the Section 4.1 model's predicted masks. 44/50 patients received a nonzero predicted infarct volume; 0/50 received a nonzero no-reflow volume, consistent with that class's 0.0 Dice score - the no-reflow features are real signal only for the 100 training patients and constant zero for the 50 test patients. This asymmetry is a direct, traceable consequence of the segmentation limitation in Section 4.1, and is flagged rather than smoothed over.

## 5. Ablation: do the new features actually improve risk classification?

The 4 infarct-burden features were added to the existing 63-feature set (67 total) and retrained under the identical protocol described in Section 3 (same Optuna search budget, same repeated stratified CV, same resampling), so any difference is attributable to the features rather than to search variance.

| Metric | Without (63 features) | With (67 features) | Δ |
|---|---|---|---|
| Accuracy | 0.927 ± 0.038 | 0.928 ± 0.035 | +0.001 |
| F1 (macro) | 0.692 ± 0.116 | 0.724 ± 0.131 | **+0.032** |
| Balanced accuracy | 0.730 ± 0.123 | 0.760 ± 0.146 | **+0.030** |
| AUC (macro, OVR) | 0.974 ± 0.022 | 0.971 ± 0.023 | -0.003 |

Accuracy and AUC are near-ceiling already and barely move, since both are dominated by the ~75% majority class. F1-macro and balanced accuracy - the metrics most sensitive to minority-class performance in a 4-class problem this imbalanced - improve meaningfully. This pattern is consistent with the new features carrying information specifically relevant to distinguishing risk categories, not just majority-class noise.

Two additional checks support this interpretation:
- **Not redundant with existing features**: the maximum absolute correlation between any of the 4 new features and any of the existing 63 is 0.72 (`infarct_pct_of_myocardium` vs. Troponin) - comfortably below the 0.95 threshold used for correlation pruning elsewhere in this pipeline.
- **Genuinely used by the model**: in a gain-based feature importance ranking of all 67 features in the final model, `infarct_pct_of_myocardium` ranks 4th and `infarct_volume_cm3` ranks 6th - ahead of most individual radiomics texture/shape features. This directly contrasts with the retired Attention-MLP branch (Section 3), which had exactly zero measured importance; here the new imaging-derived features are demonstrably load-bearing.

## 6. Final model and known limitations

**Production model**: calibrated XGBoost (`CalibratedClassifierCV`, sigmoid, 3-fold internal calibration) on 67 features (59 pruned radiomics + 4 clinical + 4 infarct-burden), hyperparameters selected by the Section 5 Optuna search: `max_depth=5, learning_rate=0.01, n_estimators=500, subsample=0.8, colsample_bytree=1.0, min_child_weight=1, gamma=0.1, reg_lambda=1.0`.

**Limitations, stated plainly:**
1. The training label is a deterministic rule over the same 4 clinical inputs used as features (Section 1), not a real clinical outcome. All accuracy figures should be read as "agreement with the rule," not "predictive of a real event."
2. No-reflow segmentation fails completely at this dataset's scale (Section 4.1); the corresponding features are only real signal for the 100 ground-truth-masked patients. A class-weighted loss fix was attempted and did not resolve it (Section 9) - the root cause appears to be too few positive pixels/patients to learn the class from, not a fixable loss-function choice.
3. `/predict` has no path that uses a real patient's own MRI-derived features - it always substitutes the training cohort's population-median value for all 63 imaging/radiomics features, regardless of whether that patient uploaded a scan via the separate `/gradcam` endpoint. This is not a fallback from a richer mode; it is the only mode `/predict` has. Confirmed harmless to accuracy on this cohort's own deterministic label (Section 1): re-running all 50 test patients with their real imaging features substituted for the median produces identical predictions to the median-imputed ones on every patient, because the label is already fully determined by the 4 clinical inputs alone - so wiring in live imaging inference would add engineering complexity and a fragile native-dependency surface (PyRadiomics conflicts with this project's pinned NumPy/TensorFlow versions) without moving accuracy on this target. It would still matter for a patent's enabling disclosure if the pipeline needs to demonstrably run end-to-end on a new patient; it is out of scope here. Median substitution can also bias predictions toward the majority (Very High Risk) class regardless of how benign the 4 clinical inputs look in isolation - present in both the pre- and post-infarct-feature models equally, not introduced by this work. A rule-based cross-check is surfaced alongside every prediction specifically to catch this disagreement.
4. All results are internal cross-validation on a single 150-patient cohort; no external validation cohort was available.
5. The segmentation model does not generalize to scans framed differently than EMIDEC's acquisition convention. Tested directly (Section 11) on a real, correctly-sequenced (LGE-MRI) scan from an independent public source: complete non-detection (100% background at 1.0 confidence on every pixel), traced specifically to framing, not sequence type or physical field-of-view - EMIDEC's images crop tightly on the heart, filling most of the frame, while the external scan's heart is real and visible but small and off-center within a wider anatomical field. The model appears to have implicitly learned "the heart fills the frame" rather than a scale/position-invariant representation of cardiac anatomy, a direct consequence of training on a single-source, single-protocol, n=100 cohort. A test-time multi-crop search was attempted as a mitigation and rejected after validation against real ground truth found it made the model substantially *less* accurate (Section 11) - this limitation is currently unresolved; the durable fix would be training on more acquisition protocols with explicit crop augmentation, not a test-time workaround.

## 7. Automated training pipeline

The ad hoc pattern used through Section 6 - separate scripts for feature pruning, hyperparameter search, and final-model training, with hyperparameters manually copy-pasted between them - was consolidated into `training/pipeline.py`: correlation pruning -> Optuna search over both hyperparameters *and* model family (XGBoost, LightGBM, regularized logistic regression) -> repeated stratified 5x5 CV evaluation -> calibration check -> a structured, git-tracked run record (`training/runs/<run_id>.json`). `training/promote_model.py` is a separate, explicit promotion step that refuses to overwrite the production model unless the candidate's F1-macro (the metric most sensitive to this project's class imbalance) beats the currently-promoted run, recorded in the same run-record system.

Extending the search to include model family, not just XGBoost's hyperparameters, is a genuine automation of a previously-fixed human choice. Re-running the identical baseline search space used in Section 3-6 (XGBoost only) reproduces those numbers closely (Accuracy 0.931±0.039 vs. the earlier 0.927±0.038; F1-macro 0.734±0.149 vs. 0.692±0.116 - within noise of each other), confirming the consolidation didn't silently change behavior. Opening the search to all three families on the same 63-feature baseline selected LightGBM in one run (Accuracy 0.908±0.061, F1-macro 0.669±0.148) - statistically indistinguishable from the XGBoost-only result given the overlapping standard deviations, illustrating exactly why the promotion gate compares against a recorded number rather than assuming a broader search is automatically better.

## 8. Transformer-fusion ablation

Extending the honest-ablation pattern from Section 5 to the README's other "future improvement" claim: a hybrid CNN-transformer fusion model, built and evaluated to test whether it beats the calibrated XGBoost baseline, not assumed to.

**Design** (`training/compute_cnn_embeddings.py`, `training/train_transformer_fusion.py`), following the small-medical-imaging-dataset literature (searched specifically for this ablation): a frozen, pretrained CNN as a fixed feature extractor rather than a transformer trained end-to-end from raw images, since the literature is explicit that pure transformers need far more data than 150 patients. The 5-class U-Net's bottleneck activations (128-dim, spatially and slice-averaged per patient) serve as the "imaging" modality; the same tabular features used elsewhere (clinical + correlation-pruned radiomics, optionally + infarct-burden) serve as the "tabular" modality. Each modality is projected to a shared width and treated as a 2-token sequence through one transformer encoder block (multi-head self-attention + feed-forward), mean-pooled, and classified - evaluated under the identical repeated stratified 5x5 CV protocol as every other model in this report.

**Result**: the fusion model does not generalize at all. Both variants (with and without infarct-burden features) score at chance level - AUC 0.537±0.108 (without) and 0.558±0.133 (with), against a 0.5 random baseline - despite 80 training epochs per fold. This was verified as genuine overfitting rather than a training bug: the identical model, fit and evaluated on the *same* data, reaches 100% training accuracy, confirming the architecture and gradient flow work correctly and the failure is purely a generalization failure at this sample size. This is a stronger, more definitive version of the Section 3 finding that the much simpler Attention-MLP branch contributed zero signal - here, a from-scratch-trained fusion head catastrophically overfits a training fold of roughly 120-150 resampled patients and learns nothing transferable to held-out ones.

**Conclusion**: transformer-based fusion is not a viable improvement for this project at its current data scale, consistent with the literature reviewed before attempting it. The calibrated XGBoost model from Section 6 remains the production model. This negative result is reported as evidence, not omitted, per this project's practice of documenting ablations honestly regardless of outcome.

## 9. No-reflow class-weighting attempt

The 5-class U-Net (Section 4.1) scores exactly 0.0 Dice on no-reflow, the rarest class (0.017% of training pixels). Plain categorical cross-entropy barely penalizes a model for never predicting a class this rare, so the natural next attempt is a class-weighted loss.

**Design** (`training/retrain_unet_5class_weighted.py`): median-frequency weighted categorical cross-entropy (Badrinarayanan et al., SegNet convention: `weight_c = median(class frequencies) / freq_c`), deliberately chosen over naive inverse-frequency weighting. Naive weighting would give no-reflow a ~5700x weight, close to the failure mode that has twice destabilized earlier U-Net retrain attempts in this project's history; median-frequency weighting keeps weights in a narrower range (background 0.014x, LV cavity 0.91x, myocardium 1.0x, infarction 7.7x, no-reflow 77.6x) while still making rare classes matter substantially more than they do unweighted. Data loading, patient-level split (same `RANDOM_STATE`, identical train/val patients), architecture, and augmentation are all unchanged from the unweighted run, so the loss function is the only variable.

**A methodology bug was found and fixed before trusting any result.** The first run used `EarlyStopping(monitor="val_loss", restore_best_weights=True)`, unchanged from the unweighted script. But per-class Dice swung wildly between checkpoints (myocardium 0.007 -> 0.220 -> 0.037 across three 5-epoch checkpoints) while `val_loss` stayed flat at 0.106-0.109 across the same span - the weighted loss is dominated by the 77.6x term over a handful of pixels, making it a poor proxy for segmentation quality. `restore_best_weights` on that metric meant the final saved model was effectively whichever epoch won a coin flip, not a representative measurement. Fixed by adding a callback that computes per-class Dice every epoch and monitoring the mean over the four foreground classes (`val_mean_fg_dice`, excluding the trivially-easy background class) instead. The run below uses the corrected criterion.

**Result** (same 20 held-out validation patients as every other number in this report):

| class | unweighted Dice | weighted Dice | delta |
|---|---|---|---|
| background | 0.9974 | 0.9392 | -0.0582 |
| LV cavity | 0.8844 | 0.2308 | -0.6536 |
| myocardium | 0.7519 | 0.0693 | -0.6826 |
| infarction | 0.2751 | 0.0000 | -0.2751 |
| no-reflow | 0.0000 | 0.0000 | +0.0000 |

No-reflow Dice remains exactly 0.0 - not an improvement. The model does predict no-reflow somewhere (16,857 pixels across the validation set), so this is not simple prediction-avoidance; those predictions have zero overlap with the true no-reflow pixels, meaning the model fires the label in the wrong locations rather than never firing it at all. Meanwhile every other foreground class suffers severe collateral damage: myocardium and LV cavity Dice both drop by roughly two-thirds, and infarction - which the unweighted model partially learned (0.2751 Dice) - collapses to 0 predicted pixels of that class anywhere in the validation set. This is not a favorable trade-off; it is a strictly worse model on every foreground class except the one it was meant to fix.

**Why this is likely a data-scarcity problem, not a loss-weighting problem**: across the full 100-patient ground-truth-masked cohort, only 40 patients have any no-reflow pixels at all, and the class totals 2,517 pixels cohort-wide (roughly 63 pixels per positive patient, spread thin across slices) - of which 915 pixels fall within the 20 held-out validation patients (about 6 pixels/slice on average across 144 val slices), leaving 1,602 pixels across the 80 training patients to learn the class's appearance from. At that scale, Dice is dominated by whether the model happens to fire on a handful of pixels in the right place, which bounds what any loss-reweighting scheme can achieve without more positive examples.

**Conclusion**: median-frequency class weighting does not fix no-reflow segmentation at this dataset's scale, and costs substantial accuracy elsewhere. `training/unet_5class_weighted.h5` is kept as a documented experiment artifact only - it must not be used by `compute_infarct_features_test.py` or any downstream feature extraction; the production segmentation model remains the unweighted `training/unet_5class.h5` from Section 4.1. This negative result is reported per this project's practice of documenting ablations honestly regardless of outcome, and narrows the no-reflow gap to what it actually is: a data-volume limitation, not a solvable loss-function tuning problem.

## 10. End-to-end validation against the live API, and a production labeling bug

The full deployed stack (FastAPI backend + Next.js frontend, run locally) was exercised end-to-end against all 50 EMIDEC test-set patients (Case_101-150) via `/predict`, `/shap`, and `/gradcam`, rather than by calling model code directly - catching integration bugs the unit tests missed.

**Bug found and fixed**: every `finalize_*.py` / `pipeline.py` training script built its risk-label mapping as `dict(zip(range(len(le.classes_)), le.classes_))` after `LabelEncoder().fit_transform(Risk_Score.astype(str))`. `le.classes_` there is just the sorted `Risk_Score` digit strings (`'0'..'3'`), not the `Risk_Category` names - so `/predict`'s `risk_class` field, and `/shap`'s, silently returned `'0'`/`'1'`/`'2'`/`'3'` instead of e.g. `'Low Risk'`. The same bug independently existed in the clinical-only fallback model (`load_or_train_clinical_model`). Both underlying classifiers were unaffected (`Risk_Score` is already a clean ordinal target; every CV number in Sections 3-9 is computed on it directly and needs no correction) - only the human-readable label attached to a prediction was wrong. Fixed at the root in all 5 scripts plus a shared `training/common.py` helper, patched into both existing production pickles, and given a regression test (`risk_class` must not be a bare digit string). The live frontend had an undocumented client-side lookup table papering over exactly this ('0' -> 'Low Risk', etc., in `frontend/lib/risk.ts`), so end users were never shown raw digits - but any other consumer of the API directly would have been.

**What this test does and does not demonstrate about accuracy**: Case_101-150 have no ground-truth segmentation masks, but they are *not* held out from the tabular model - Section 1 already notes the reported n=150 pools all patients together, and `combined_radiomics_features.csv` includes clinical values, engineered features, and a rule-derived `Risk_Category` for all 150, including 101-150 (their imaging-derived features come from the Section 4.1 model's own predicted masks, per Section 4.2). The currently-promoted production model (`training/finalize_infarct_model.py`) fits on all 150 resampled rows directly with no train/test split at all. So the 50/50 agreement between `/predict` and the independent rule-based classifier observed while fixing the labeling bug is the model matching labels it was fit on (and that are themselves a deterministic function of the same 4 inputs, per Section 1) - it is not external validation and should not be read as a generalization result. It is, however, real confirmation that the pipeline runs correctly end-to-end without crashing on every patient in the cohort.

**What genuinely is external validation here**: the Section 4.1 U-Net was trained only on the 100 ground-truth-masked patients (`emidec-dataset-1.0.1`); Case_101-150 never contributed a single pixel-level label to it. Running all 50 of their raw MRI volumes through the live `/gradcam` endpoint completed with zero crashes, and a spot-check of the returned overlays showed a correctly-localized, ring-shaped myocardium activation consistent with the training-set behavior in Section 4.1 - genuine (qualitative, not Dice-scored, since no ground truth exists for this partition) evidence that the segmentation model generalizes to unseen scans rather than memorizing training-set anatomy. One case (Case_148) produced a visibly noisier overlay background, traced to `preprocess_volume_for_unet`'s global min-max normalization being sensitive to a single outlier-intensity voxel; the segmentation ring itself still localized correctly, so this is logged as an intensity-normalization robustness limitation, not a functional failure.

**Would wiring real imaging features into `/predict` change anything?** `/predict` always substitutes population-median values for all 63 imaging/radiomics features (Section 6, limitation 3), even for a patient who separately uploaded a real MRI. To test whether this is worth fixing, each of the 50 test patients' actual imaging-feature row (already present in `combined_radiomics_features.csv`, extracted from the Section 4.1 model's predictions) was substituted for the median and compared against today's median-imputed prediction. Result: identical predicted class on all 50/50 patients - real imaging features changed nothing. This follows directly from Section 1: the label is a deterministic function of the 4 clinical inputs alone, so those inputs already determine the answer completely, and no amount of additional real feature data can move a prediction away from what the rule already fixed. Building live imaging inference into `/predict` (a new 5-class-model + PyRadiomics extraction path) was therefore not implemented this session - it would add a fragile native-dependency surface (PyRadiomics's declared NumPy>=2.0 requirement conflicts with this project's pinned NumPy 1.26.4/TensorFlow 2.15.0) for zero measured accuracy benefit on the only label available. It would still be worth building if a patent's enabling disclosure specifically needs the full pipeline demonstrated end-to-end on a new patient - that is a scope decision, not an accuracy one.

**Conclusion**: this session fixed a real, previously-undiscovered production bug, and adds genuine (if qualitative) external-validation evidence for the segmentation model. It does not add new evidence for the tabular risk-classification model's accuracy - Section 1's existing caveat about the rule-derived label already covers why, and no claim in this report should cite the 50-patient agreement figure as validation. It also settles that wiring live imaging features into `/predict` would not, by itself, improve that model's agreement with its own training label.

## 11. Testing the actual deployed frontend in a browser, and generalization to a non-EMIDEC scan

Section 10's testing called the API directly (curl, Python). A separate pass drove the real Next.js frontend in an actual browser, since that exercises the exact request pattern a user produces - which turned out to matter.

**A second, more serious concurrency bug, found only by browser testing**: the frontend fires `/predict` and `/shap` in parallel on every form submission (`Promise.allSettled`). On a freshly started backend, the first real submission came back tagged `clinical_only` instead of `calibrated_xgboost`, with different (and materially different) probabilities than the same request made serially. Root cause: both handlers raced to trigger Python's first `import xgboost` - one implicitly, via `joblib.load` unpickling a stored `XGBClassifier`; the other explicitly, inside `try_shap_from_best_model`. `xgboost` has internal circular submodule imports (`xgboost.callback` / `xgboost.sklearn` / `xgboost.training`) that are not safe against two threads triggering the first import simultaneously, and this raised `ImportError`/`KeyError` inside `predict_with_calibrated_xgb`, which `main.py` catches silently and downgrades to the clinical-only model - no error logged anywhere. This means **every fresh backend restart's first real user got a silently worse model**, indistinguishable from a normal response. curl and direct function calls never reproduce this, since neither races the import the way two concurrent request threads do. Reproduced reliably (10/10) in isolation via a threaded repro script, fixed by importing `xgboost` eagerly at `ml.py`'s module load time instead of lazily inside request handlers, verified fixed (0/10 in the repro; correct model tag on a live fresh-restart browser submission), and given a subprocess-based regression test (the bug only reproduces on a truly cold import, so the test spawns a fresh interpreter rather than reusing the already-warm test process).

**Generalization to a real, non-EMIDEC LGE-MRI scan**: a single example LGE-MRI slice (`rawimage.nii`, ~5.5 MB) was sourced from a public, CC-BY-4.0-licensed research repository ([`GabrielBalabanResearch/lgemri_scar_metrics`](https://github.com/GabrielBalabanResearch/lgemri_scar_metrics)) - genuinely external to EMIDEC, and the correct sequence type (LGE, the same contrast mechanism EMIDEC uses to visualize infarct), unlike the more commonly available cine-MRI datasets. Run through the live `/gradcam` endpoint (via both curl and the browser): no crash, but the U-Net predicted background for 100% of pixels with 1.0000 confidence - complete non-detection, not a low-confidence miss.

Diagnosis, not just observation: rendering both images exactly as the network receives them (resized to 128x128) showed the mechanism directly. EMIDEC's acquisition crops tightly on the heart, which fills most of the frame at this resolution. The external image's heart, while real and clearly visible in the raw scan, is a smaller, off-center feature within a much wider anatomical field (ribs and surrounding chest wall dominate the frame) - a different acquisition/framing convention, not a difference in physical field-of-view (215x356mm for the EMIDEC example vs. 400x275mm for the external image - comparable order of magnitude). The model appears to have implicitly learned "the heart fills the frame" from EMIDEC's consistent cropping convention, and does not generalize to images where it doesn't. This is a genuine, evidenced robustness limitation for a n=100-patient, single-source segmentation model, distinct from (and more informative than) the Case_148 intensity-normalization note in Section 10.

**Attempted test-time fix, tested against real ground truth, and rejected**: since the network appears to expect "heart fills the frame," `localize_and_preprocess_volume()` (`backend/app/ml.py`) was built to search five center-crop fractions (1.0 down to 0.35) per slice at inference time, keeping whichever crop produced the highest total cavity+myocardium probability mass, before running the normal pipeline - no retraining required. On the failing external scan this looked like a clear win: 0 detected pixels of any foreground class became a real, correctly-located partial detection right on the visible myocardial wall. It also *increased* predicted foreground pixel counts on several EMIDEC test-set cases (Case_101, 110, 120, 130, 140, 148, 150) relative to the baseline.

That was the wrong metric to trust. Pixel count is not accuracy, and Case_101-150 have no ground truth (Section 1) to check it against. Validated instead against real ground-truth Dice on 15 EMIDEC *training* patients (which do have Contours) - comparing the baseline full-frame resize against the crop search, cropping and resizing the ground-truth mask identically to whatever crop was chosen for each slice:

| | Baseline (current, unchanged) | Crop-search mitigation |
|---|---|---|
| Cavity Dice (mean, 15 patients) | 0.884 | 0.781 |
| Myocardium Dice (mean, 15 patients) | 0.833 | **0.528** |

The crop search was picking tighter crops that made the network predict larger blobs, not more *correct* ones - a substantial, real accuracy regression, not a wash. `generate_gradcam_overlay` was **not** changed to use this function; it still calls the original, validated `preprocess_volume_for_unet`. `localize_and_preprocess_volume` is kept in the codebase only as a documented, tested, and rejected attempt (see its docstring), following this project's practice of keeping negative results (e.g. Section 9's weighted U-Net) as traceable artifacts rather than deleting the evidence. The framing-mismatch limitation itself remains open and unresolved - the durable fix is training on a more diverse, multi-protocol cohort with explicit crop/framing augmentation, not a test-time workaround.

**A second external source, testing the framing hypothesis rather than just the sequence-type question**: a single whole-heart volume (`la_007.nii.gz`, 15.5 MB, 320x320x130) was extracted directly from the Medical Segmentation Decathlon's Task02_Heart tar ([`Novel-BioMedAI/Medical_Segmentation_Decathlon` on Hugging Face](https://huggingface.co/datasets/Novel-BioMedAI/Medical_Segmentation_Decathlon), streamed and stopped after the first training image so the full 456 MB archive was never downloaded). This dataset is a different sequence entirely (whole-heart MRA-style imaging for left-atrium segmentation, not LGE) and a different anatomical target than EMIDEC - a worse sequence-match than Section 11's first external test, but the heart appears reasonably centered and frame-filling at a well-chosen slice, similar to EMIDEC's convention. Run through the unmodified, validated `/gradcam` endpoint: a real, correctly-located ring-shaped detection (slice 41/130, 294 cavity pixels + 173 myocardium pixels, comparable in scale to the frontend's own synthetic demo volume - see below), not the complete non-detection seen on the LGE scan.

This is consistent with, and supports, the framing diagnosis over a sequence-type explanation: a scan from an entirely different vendor/protocol/anatomical target generalized reasonably when its framing happened to resemble EMIDEC's convention, while a scan of the *correct* sequence type (LGE-MRI) failed completely when its framing did not. Framing/centering, not sequence type, appears to be the dominant factor in whether this segmentation model detects anything at all on out-of-distribution input. Confirmed a second time through the actual deployed frontend (not just curl): all 20 real training volumes in this archive are naturally 10-16 MB, too large for the browser-automation tool used for this testing session (a 10 MB cap unrelated to the app, which accepts up to 100 MB), so the same real volume was losslessly downsampled 2x (320x320x130 -> 160x160x65, a standard resampling operation, not a different or fabricated scan) to fit; the browser rendered a strong, well-formed ring, comparable in quality to a real EMIDEC patient.

**For calibration, the frontend's own built-in synthetic demo volume** (`frontend/public/sample_cardiac_mri.nii.gz`, a simple bright disc on noise, explicitly labeled in the UI as "synthetic test data, not a real patient scan") was also run through the same unmodified endpoint: partial detection (peak 508 cavity / 195 myocardium pixels at its best of 12 slices), weaker than a real EMIDEC patient's typically-complete ring but stronger than the failing LGE case - plausible for a shape that only loosely resembles real cardiac anatomy. All three points on this spectrum (real EMIDEC patient: complete ring; synthetic demo shape: partial; off-center real external scan: none) are internally consistent with each other, not contradictory anecdotes.

## 12. Isotropic in-plane resampling: a real, validated fix for the Section 11 generalization failure

Following the roadmap this section's own diagnosis pointed at (and the literature review that grounded it - nnU-Net's standard practice of resampling to a common physical voxel spacing before any pixel-grid resize, and CaRe-CNN's use of the same principle for this exact EMIDEC/MYOSAIQ problem family), `training/imaging_common.py` was built as a shared preprocessing module and `training/retrain_unet_5class.py` was retrained as `training/retrain_unet_5class_isotropic.py` using it, replacing naive pixel resize + global min-max normalization with isotropic in-plane resampling (to 1.4583mm, the median in-plane spacing across the 100-patient training cohort) + percentile (10th/90th) intensity normalization.

**Deliberate deviation from nnU-Net's default**, documented rather than silently applied: only the in-plane (X, Y) axes are resampled, not the through-plane (Z) axis. EMIDEC's acquisition is highly anisotropic (~1.46mm in-plane, 10mm slice thickness), and this project's models consume independent 2D slices, not 3D volumes - resampling Z would synthesize interpolated slices between real acquired ones, which helps nothing for a per-slice pipeline and risks interpolation artifacts for no benefit. See `training/imaging_common.py`'s docstring for the full reasoning.

**Result: a genuine improvement, validated two ways, not one.**

Real held-out Dice (identical 20 validation patients as every other model in this report):

| Class | Baseline (`retrain_unet_5class.py`) | Isotropic resample + percentile normalize |
|---|---|---|
| Background | 0.997 | 0.997 |
| LV cavity | 0.884 | 0.879 |
| Myocardium | 0.752 | 0.752 |
| Infarction | 0.275 | **0.329** |
| No-reflow | 0.000 | 0.000 |

No regression on cavity or myocardium, and a real infarction improvement (+0.054) - not a wash, and not the "looks fine" trap that sank the Section 11 crop-search attempt, since this was checked against real ground truth from the start. No-reflow stays at exactly 0.000, consistent with Section 9's data-scarcity conclusion (2,517 total positive pixels) rather than evidence against this specific fix - a preprocessing change to inputs a rare class barely appears in wasn't expected to fix that on its own.

Then, critically, **re-tested against the exact same two external artifacts that exposed the original failure**: the external LGE scan (Section 11, first test) went from 100% background at 1.0 confidence - complete non-detection - to real, correctly-typed detection: 79 LV-cavity pixels, 76 myocardium pixels, 33 infarction pixels. The MSD Task02_Heart volume's detection also strengthened (9,652 cavity / 2,604 myocardium / 6,787 infarction pixels, up from the baseline's 294/173 at its single best slice). This is the actual failure mode the fix targeted, tested directly, not inferred from internal metrics alone - the isotropic resampling hypothesis is now a validated result, not a hopeful one.

**Not yet promoted to the live `/gradcam` endpoint.** This retrain used the 5-class model family (`training/retrain_unet_5class.py`'s architecture); the model actually served live is the 3-class `unet_multiclass.h5`, trained and used separately (Section 4.1 explains why - it remains in production for the Grad-CAM myocardium-attention feature specifically). Promoting this fix to production would mean retraining that 3-class model with the same isotropic preprocessing and updating `backend/app/ml.py` to match (it currently keeps its own copy of the naive preprocessing, duplicated across the backend/training deployment boundary) - a deliberate, separate decision, not bundled into this experiment.

## 13. Cascaded segmentation architecture: real per-stage results, a net regression end-to-end

Also per the roadmap (CaRe-CNN's and the official EMIDEC challenge's own best-result methodology: cascade rather than single-shot multi-class softmax), `training/retrain_unet_cascaded.py` implements a 3-stage cascade - Stage 1 (background / LV cavity / myocardium-total), Stage 2 (healthy myocardium vs. infarct, within Stage 1's myocardial region), Stage 3 (infarct-only vs. no-reflow, within Stage 2's infarct region, using CaRe-CNN's paired per-batch sampling technique: every batch guaranteed at least one no-reflow-positive slice and one without) - built on top of Section 12's isotropic preprocessing, so any difference from Section 12's result is attributable to the architecture, not a preprocessing confound.

**Per-stage results (each stage evaluated with ground-truth previous-stage inputs - teacher forcing, the standard way to train a cascade stably) looked strong in isolation**: Stage 2 scored 0.9415 Dice on healthy myocardium and 0.7010 on infarct-vs-healthy within the myocardial region; Stage 3 scored 0.9488 on infarct-only vs. 0.6616 on no-reflow within the infarct region - both far above what the single-shot model achieves on the equivalent distinction.

**The full pipeline, evaluated the honest way - real inference with each stage's own actual prediction feeding the next, not teacher forcing - tells a different story:**

| Class | Baseline | Isotropic (Section 12) | Cascade (real inference) |
|---|---|---|---|
| Background | 0.997 | 0.997 | 0.996 |
| LV cavity | 0.884 | 0.879 | 0.844 |
| Myocardium | 0.752 | 0.752 | 0.679 |
| Infarction | 0.275 | 0.329 | 0.183 |
| No-reflow | 0.000 | 0.000 | **0.033** |

This is a real, honest, mixed result, not a clean win: no-reflow gets a genuine non-zero Dice for the first time in this project's history (0.033) - far short of CaRe-CNN's 72% on a 439-volume, multi-center cohort, but a real, measurable signal on this 100-patient one, consistent with the idea that the cascade's mechanism (explicit paired sampling, decision narrowed to an already-localized region) does something a single softmax over all 5 classes at once cannot. But every other class regresses relative to both the baseline and Section 12's isotropic model - cavity, myocardium, and infarction are all worse than either single-shot alternative. On the external validation artifacts, the cascade did not reproduce Section 12's external win either: the LGE scan still shows complete non-detection (0 pixels of any foreground class), and the MSD volume's detection is markedly weaker than Section 12's isotropic model (1,696 cavity / 493 myocardium / 141 infarction / 25 no-reflow, versus Section 12's 9,652 / 2,604 / 6,787 / 0).

**Diagnosis**: the gap between "each stage looks excellent in isolation" and "the full pipeline is worse than a single-shot model" is classic cascade error compounding - Stage 1's own imperfect myocardium boundary (a 3-class decision, itself slightly weaker in isolation than the isotropic single-shot model's direct myocardium output) limits what Stage 2 can recover within that region, and Stage 2's errors likewise propagate into Stage 3. The teacher-forced per-stage numbers measure each stage's ceiling given a perfect upstream input, not what the deployed system would actually achieve.

**Conclusion: not promoted.** The cascade is not a net improvement over Section 12's isotropic model on this 100-patient cohort - it trades a first-ever non-zero no-reflow signal for a real regression on every other class, both internally and on external validation. This is reported as a genuine, informative negative result per this project's established practice (Sections 8, 9): the mechanism CaRe-CNN uses for the rare class does appear to help that specific class even at this smaller scale, but a hand-built 3-model cascade introduces enough end-to-end error compounding to lose more than it gains, at least in this implementation. `training/retrain_unet_cascaded.py`, `training/unet_cascaded_stage{1,2,3}.h5` are kept as documented, tested artifacts. Confirming whether a properly-engineered cascade (e.g., joint fine-tuning of all three stages end-to-end after this per-stage pretraining, which CaRe-CNN's own approach implies but this implementation does not attempt) closes the gap is future work, not something this result already answers.

## 14. Promoting the isotropic fix to the live model, and a real accuracy/robustness trade-off

Section 12 validated isotropic in-plane resampling on the offline 5-class model with no internal cost. The model actually served by `/gradcam` is a separately-trained 3-class model (`unet_multiclass.h5`), so the fix was retrained there too (`training/retrain_unet_patient_split_isotropic.py`) before any promotion decision - Section 12's result does not automatically transfer to a differently-trained model.

**First attempt (10th/90th percentile clipping, matching Section 12 exactly) showed a real cost this time**, evaluated against the live model's actual documented native-preprocessing baseline (Section 4.1: cavity 0.926, myocardium 0.810):

| | Live baseline | 10/90 clip |
|---|---|---|
| LV cavity Dice | 0.926 | 0.871 (-0.056) |
| Myocardium Dice | 0.810 | 0.707 (-0.104) |
| External LGE scan | 0 (complete failure) | real detection (117 cavity + 207 myocardium px) |
| External MSD volume | 467 px (weak) | 26,259 px |

A ~10-point myocardium Dice cost for a 3-class model is more severe than the 5-class model's near-zero cost (Section 12) - plausibly because the 5-class model's other classes (infarction, no-reflow) already provide auxiliary training signal/regularization the 3-class task doesn't have, though this is not confirmed, just the most likely explanation on hand.

**Searched the percentile-clipping width for a better trade-off** (`training/imaging_common.py`'s percentile bounds made configurable specifically for this search), since 10/90 is a fairly aggressive clip and myocardium - "the thinnest, most spatially precise class" per this project's own earlier notes - seemed like a plausible casualty of discarding 20% of the intensity range:

| Percentile bounds | Cavity Dice | Myocardium Dice | External LGE detection | External MSD detection |
|---|---|---|---|---|
| Live baseline (native preprocessing) | 0.926 | 0.810 | 0 px | 467 px |
| 10/90 | 0.871 | 0.707 | 324 px | 26,259 px |
| 1/99 | 0.882 | 0.723 | 57 px | 3,880 px |
| 5/95 | 0.861 | 0.710 | 26 px | **49,739 px** |

**This is not a clean, monotonic dial.** 5/95 sits between 1/99 and 10/90 on the percentile axis but not on any of the four measured outcomes - it has the weakest LGE detection of the three *and* the strongest MSD detection, while its Dice is roughly tied with 10/90 despite the tighter clip. With only one training run per setting (no repeated-CV averaging, which would be the correct way to separate a real percentile effect from run-to-run initialization/shuffling noise, but was judged too expensive to run three times over for this exploration), the honest conclusion is that single-run noise is comparable in size to whatever true effect the percentile choice has. No setting cleanly dominates.

**Decision: promoted 1/99** (`unet_multiclass.h5` replaced; the pre-promotion model backed up unmodified at `training/unet_multiclass_original_naive_preprocessing_backup.h5` for a trivial rollback) - the best-on-Dice of the three tried, and still a real, qualitative fix for the complete external detection failure, even if the smallest-magnitude one of the three. This was an explicit user decision made with the full trade-off table in hand, not a default or an assumption that "external robustness" automatically outweighs "in-distribution accuracy" - the myocardium cost is real (0.723 vs. 0.810 native) and should be weighed against how likely this system is to actually receive non-EMIDEC-framed scans in practice.

`backend/app/ml.py`'s `preprocess_volume_for_unet` was updated to match (isotropic in-plane resample to 1.4583mm + 1st/99th percentile normalization, replacing the naive global min-max it used before) - serving the new model with the old preprocessing would have silently mismatched what it was trained on. `load_nii_volume`'s return signature changed from `vol` to `(vol, spacing_xy)` to carry the needed spacing metadata through to preprocessing; `main.py` and `generate_gradcam_overlay` were updated accordingly. Verified end-to-end through the real API and the actual browser (not just curl or a standalone script) on both a real EMIDEC patient (still a coherent, correctly-located ring, visibly weaker-intensity than before - consistent with the measured Dice cost) and the external LGE scan (a real, correctly-located hotspot on the visible myocardial wall, where there was previously nothing at all).

**Not yet deployed to production** - this promotion is local (the repo's `unet_multiclass.h5` and `backend/app/ml.py`). Pushing it live requires the documented redeploy flow (rebuild the Docker image, push to GHCR, trigger a Render redeploy - see README's Redeploying section), a separate step from this local promotion.
