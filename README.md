# An Explainable Multi-Modal Deep Learning Framework for Cardiac Risk Stratification

### Overview
This is the Web Application link of the Project: https://cardiac-risk-frontend.vercel.app

This project presents an **explainable AI pipeline** for predicting patient-specific cardiac risk levels by integrating **cardiac MRI images** and **structured clinical data**.
It combines deep learning–based **myocardial and infarct-region segmentation**, **radiomics and infarct-burden feature extraction**, and **multi-modal risk prediction** using a **calibrated XGBoost** classifier with **SHAP + Grad-CAM explainability**.

### Known limitation: the training label is a rule, not an outcome

The 4-class risk label every model is trained on (`Risk_Category`/`Risk_Score` in `combined_patient_risk_classification.csv`) is generated by `classify_patient_risk_rule_based()` - a deterministic set of thresholds on Age/LVEF/Troponin/NT-proBNP - not a real clinical outcome (e.g. a documented MACE, hospitalization, or mortality event at some follow-up horizon). Since those same four values are also fed into every model as clinical input features, the models are partly learning to reproduce a formula of their own inputs; the radiomics/imaging features are the only source of information not already fully determined by the label itself. Treat this project's models as **rule-imitation models validated against that rule**, not as outcome-predictive models - that distinction matters when interpreting any accuracy number reported here. Fixing this would require sourcing real patient outcome data, which is outside what this codebase can do on its own.

### Known limitation: clinical-only predictions default to population-median imaging features

`POST /predict` and `GET /shap` accept only the 4 clinical inputs (age, LVEF, troponin, NT-proBNP) - no MRI upload. Since the production model's remaining ~63 features are radiomics/infarct-burden values derived from imaging, a clinical-only request fills them with the training population's median values and only overrides the 4 clinical fields. Because ~75% of the training cohort is "Very High Risk," that median imaging profile looks sick, which can bias predictions toward Very High Risk even for clinical inputs that look benign in isolation - this was confirmed present in both the pre- and post-infarct-feature models, so it is not a regression from any specific model version. The rule-based cross-check shown alongside every prediction exists specifically to catch this disagreement. A real fix would mean either requiring an MRI upload before returning a model-based prediction, or building a clinical-only model trained without the imaging features - out of scope for the current codebase.

A related, more specific symptom shows up in `/shap`: Troponin's reported SHAP contribution can come out bit-for-bit identical across very different raw inputs (e.g. 0.01, 0.08, and 4.5 ng/L all produced the exact same contribution value in testing). This was traced down to the booster level and confirmed to not be a code defect - `pred_contribs` does respond correctly to sufficiently different scaled inputs when tested directly against the model. The actual cause is the training population's Troponin distribution: mean ~70, std ~94 (a handful of extreme acute-MI patients dominate the scale), so raw values anywhere in the roughly 0-25 range collapse into the same narrow low z-score band (around -0.74 to -0.70) that none of the trained trees ever split within. The model has no learned resolution to distinguish "undetectable" from "mildly elevated" troponin at that end of the range - the same underlying small-sample/skewed-population limitation as above, just visible in the explainability output as well as the prediction itself.

### Known limitation: the 5-class segmentation model cannot learn the no-reflow class

The infarct-burden features (`infarct_volume_cm3`, `infarct_pct_of_myocardium`, `no_reflow_volume_cm3`, `no_reflow_pct_of_infarct`) come from a U-Net extended to predict 5 classes instead of 3 (adding infarction and no-reflow/microvascular obstruction, previously discarded). It learns infarction reasonably (Dice 0.275, non-trivial at only 0.176% of training pixels) but scores 0.0 Dice on no-reflow, which is 10x rarer (0.017% of pixels) - effectively unlearnable from EMIDEC's 100 training patients alone. The no-reflow-derived features are real signal only for the 100 patients with ground-truth masks; for the 50 test patients (predicted masks), `no_reflow_volume_cm3` and `no_reflow_pct_of_infarct` are constant zero. More annotated data would be needed to fix this.

## Architecture

A decoupled backend/frontend stack. `HeartRiskStratificationq3.ipynb` and `heartriskstratificationq4.py` hold the model training and evaluation work; `training/` holds the automated training pipeline described below.

**Backend (`backend/`)** - a FastAPI service. `backend/app/ml.py` holds the model-loading and inference logic (clinical LogisticRegression fallback model, a single calibrated XGBoost classifier, U-Net Grad-CAM utilities, and SHAP explainers via XGBoost's native `pred_contribs`), with a best-model-first/clinical-fallback behavior. A single calibrated XGBoost model is used in production; a stacked XGBoost + Attention-MLP ensemble was evaluated and dropped after permutation importance showed the Attention-MLP branch contributed zero signal, so it matches the ensemble's accuracy with far less complexity. `backend/app/main.py` exposes it as REST endpoints:

* `GET /health` - liveness check.
* `POST /predict` - clinical inputs (age, LVEF, troponin, NT-proBNP) in, risk class + per-class probabilities out. Tries the calibrated XGBoost model first, falls back to the clinical-only model on failure.
* `GET /shap` - SHAP feature contributions for the same clinical inputs.
* `POST /gradcam` - accepts an uploaded `.nii`/`.nii.gz` MRI volume, returns a base64 PNG Grad-CAM myocardium overlay plus the selected slice index. Uploads are capped at 100MB, streamed to disk in chunks and rejected with `413` if the limit is exceeded before any model work happens.

All four endpoints (`/health`, `/predict`, `/shap`, `/gradcam`) have been verified against the live deployed Render backend, each returning a real response (a synthesized `.nii.gz` test volume was used for `/gradcam`, since no sample MRI is committed to the repo).

**Frontend (`frontend/`)** - a Next.js (App Router, TypeScript, Tailwind v4) clinical dashboard: a clinical-inputs form, a risk/probability result view with a rule-based cross-check, a SHAP contribution chart, and a Grad-CAM MRI upload/viewer. Dark mode only, responsive down to mobile. It talks to the backend through a single configurable env var, `NEXT_PUBLIC_API_BASE_URL` (see `frontend/.env.local.example`).

### Live deployment

* Backend: [Render](https://render.com) (Docker runtime, free plan), at `https://cardiac-risk-backend.onrender.com`, deployed from a pre-built image (see Redeploying below). Being on Render's free plan, the instance spins down after inactivity and the first request after a period of idleness can take up to a minute to respond while it wakes up.
* Frontend: Vercel, at `https://cardiac-risk-frontend.vercel.app`.

The deployed frontend has been verified end-to-end in a real browser against the deployed backend: submitting the clinical-inputs form returns a real calibrated-XGBoost prediction and real SHAP contributions, with no console errors.

### Running locally

Backend:

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

`ml.py`'s `MODEL_DIR` defaults to the repo root, two directories above `backend/app/ml.py`, so the committed model artifacts (`clinical_model.pkl`, `best_prognostic_model.pkl`, `unet_multiclass.h5`, `combined_radiomics_features.csv`) are picked up automatically without copying them into `backend/`. Override with the `MODEL_DIR` env var if needed.

If port 8000 is already taken on your machine, pass a different `--port` and update the frontend's API base URL to match.

**Backend tests:** `backend/tests/test_api.py` covers the rule-based reasoning branches, and `/health`, `/predict`, `/shap`, `/gradcam` against the real committed model artifacts. Run with:

```bash
cd backend
pip install -r requirements-dev.txt
pytest tests/ -v
```

Frontend:

```bash
cd frontend
cp .env.local.example .env.local   # set NEXT_PUBLIC_API_BASE_URL to your backend URL
npm install
npm run dev
```

By default this serves on `http://localhost:3000`; if that port is occupied, Next.js will pick the next free one (e.g. 3001) and print it in the terminal. The backend's `CORS_ORIGINS` defaults to `http://localhost:3000`, so if the frontend lands on a different port, set `CORS_ORIGINS` on the backend to match, or requests will fail with "Disallowed CORS origin".

**Frontend tests:** `frontend/lib/*.test.ts` covers `lib/risk.ts` (risk-label mapping, and the ordering-sensitive "very high" vs "high" color-accent branches) and `lib/api.ts` (error-detail parsing from JSON vs non-JSON backend error bodies). Uses Node's built-in test runner, no extra dependencies. Run with:

```bash
cd frontend
npm test
```

### Redeploying

**Backend (Render):** the Render service is configured for image-based deploys, not git-triggered ones. To redeploy after changing the backend, build and push a new image, then trigger a deploy against it:

```bash
docker build -f backend/Dockerfile -t ghcr.io/kbssrikar7/cardiac-risk-backend:latest .
docker push ghcr.io/kbssrikar7/cardiac-risk-backend:latest

curl -X POST "https://api.render.com/v1/services/<service-id>/deploys" \
  -H "Authorization: Bearer $RENDER_API_KEY" -H "Content-Type: application/json" \
  -d '{"clearCache":"do_not_clear"}'
```

`backend/Dockerfile` is built from the repo root (it copies the model artifacts and `backend/app` directly from this repo) - no separate deploy repo is involved.

Env vars (e.g. `CORS_ORIGINS`, set to the frontend's stable production origin - see below) are set the same way, via `PUT /v1/services/<service-id>/env-vars`; changing them does not auto-restart the service, so follow up with a deploy trigger as above. Render's Docker services listen on port 7860 by default (`backend/Dockerfile`'s `ENV PORT=7860`).

**Frontend (Vercel):** with the Vercel CLI authenticated and the project linked (`vercel link`):

```bash
vercel env add NEXT_PUBLIC_API_BASE_URL production   # point at the backend's public URL
vercel --prod
```

Each `vercel --prod` run also mints a fresh per-deployment hash URL (e.g. `cardiac-risk-frontend-<hash>-<team>.vercel.app`) in addition to the stable production alias (`cardiac-risk-frontend.vercel.app`). The backend's `CORS_ORIGINS` should include the stable alias, since that's what stays constant across deploys; a request from a stale per-deployment hash URL will get "Disallowed CORS origin" once a newer deployment has been promoted.

## Key Features

* **Multi-Modal Fusion:** Combines radiomics features from cardiac MRI with clinical biomarkers (LVEF, NT-proBNP, Troponin, Age).
* **Automated Myocardium Segmentation:** Trained U-Net model identifies myocardium from short-axis MRI slices.
* **Radiomics Extraction:** Quantitative shape, texture, and intensity features computed using *PyRadiomics*.
* **Risk Prediction Model:**

  * A single calibrated XGBoost classifier (`CalibratedClassifierCV`), tuned via nested Optuna search and evaluated with repeated stratified cross-validation. An earlier stacked XGBoost + Attention-MLP ensemble was retired after permutation importance showed the MLP branch contributed zero signal.
* **Explainability:**

  * **Grad-CAM** – visual heatmaps highlighting myocardial regions driving predictions.
  * **SHAP** – feature-level explanations showing how clinical and radiomic features influence each prediction.
* **Result Output:** Predicts risk class → *Low, Moderate, High, Very High* with visual & quantitative explanations.

## Implementation Workflow

1. **Data Preparation**

   * Load cardiac MRI & clinical CSV data.
   * Preprocess images and normalize clinical variables.

2. **Segmentation (U-Net)**

   * Train on EMIDEC dataset; output predicted myocardium masks.

3. **Feature Extraction**

   * Use *PyRadiomics* to extract texture, shape, and first-order features.
   * Merge with clinical parameters into `combined_radiomics_features.csv`.

4. **Model Training**

   * Balance data using SMOTE + RandomUnderSampler.
   * Train a calibrated XGBoost classifier via nested Optuna hyperparameter search.

5. **Explainability Analysis**

   * **SHAP:** global feature importance & per-patient waterfall plots.
   * **Grad-CAM:** visualize MRI regions influencing predictions.

6. **Output**

   * Predicted risk category (Low / Moderate / High / Very High).
   * Visual explanations (Grad-CAM + SHAP).

## Explainability Modules

### SHAP (SHapley Additive exPlanations)

* Quantifies the impact of each input feature on model output.
* Provides both **global** (overall feature influence) and **local** (individual patient reasoning) interpretability.
* Example:

  * **High NT-ProBNP** and **Low LVEF** push the prediction toward **High/Very High Risk**.
  * **Normal Troponin and LVEF** lower the predicted risk level.

### Grad-CAM (Gradient-weighted Class Activation Mapping)

* Highlights the **specific myocardial regions** that most influenced the model’s decision.
* Produces a color heatmap overlay (red = high influence, blue = low influence).
* Enables clinicians to **verify the anatomical areas** responsible for the prediction, improving trust.

Together, **SHAP + Grad-CAM** make the system *transparent, interpretable, and clinically reliable*.

## Future Improvements

Ordered by what's actually achievable without new institutional partnerships, not by ambition:

* **AutoML pipeline for automated hyperparameter optimization and retraining** - in progress: `training/pipeline.py` searches hyperparameters *and* model family (XGBoost / LightGBM / logistic regression) via Optuna, evaluates under repeated stratified CV, and writes a versioned run record; `training/promote_model.py` gates production promotion on beating the currently-promoted run. See `training/runs/README.md`.
* **Transformer-based fusion models for cross-modal learning** - in progress as an honest ablation, not an assumed upgrade: literature on small medical-imaging datasets (searched; see `training/TECHNICAL_REPORT.md`) confirms pure transformers need far more data than this project's 150 patients, and this project's own Attention-MLP branch already measured zero signal at this scale. A hybrid CNN-transformer variant is being evaluated under the same CV protocol as everything else, expecting a negative or marginal result worth reporting either way.
* **Expand to larger, multi-center MRI datasets** for stronger generalization - not achievable solo; requires hospital partnerships, IRB approval, and data-sharing agreements this project doesn't currently have.
* **Integrate federated learning** for privacy-preserving multi-hospital collaboration - downstream of the item above; there's nothing to federate across without multiple institutions already holding their own data.

(A web-based clinical dashboard for real-time risk evaluation was also on this list - the FastAPI/Next.js app described above already is that, so it's been removed as a "future" item.)
